# SS Bills — Decision Log

Record every product or technical decision here with the date and reason. Newest at the bottom.
Open questions live in their own section until resolved.

## Decisions

| ID | Date | Decision | Reason |
|---|---|---|---|
| D-001 | 2026-10-21 | **Offline-first with local SQLite** on each restaurant's PC holds all bill-level data | Billing must never stop when the internet drops. SQLite is free, needs no server, and backup is a single file |
| D-002 | 2026-10-21 | **Supabase** is the central vendor backend, for license authentication and consolidated daily summaries | One free service covers auth, Postgres, and an admin dashboard. SQL suits reports |
| D-003 | 2026-10-21 | Central server stores **only daily summaries** (sales, bill count, payment split, tax, top item), not full bills. Monthly figures are derived from the daily rows | Owner's choice: keep central data small, and keep detailed data with the restaurant |
| D-004 | 2026-10-21 | **WhatsApp bill sharing removed** for now | Owner's choice. The non-API (`wa.me`) approach can't attach PDFs; revisit later |
| D-005 | 2026-10-21 | **No discounts** | Owner's choice |
| D-006 | 2026-10-21 | Added to scope: table numbers, order types (dine-in, takeaway, delivery), held bills, sequential bill numbers, KOT, CGST/SGST split, optional service charge | Accepted from the review of the original plan |
| D-007 | 2026-10-21 | Support **58mm and 80mm thermal printers**, plus PDF | Standard restaurant hardware. Method superseded by D-023 |
| D-008 | 2026-10-21 | Two roles only: **Admin** and **Cashier** | Keep it simple; only Admin edits prices, cancels bills, and sees reports |
| D-009 | 2026-10-21 | Bills are **never hard-deleted**; they are cancelled with a reason and kept for audit | GST compliance and fraud prevention |
| D-010 | 2026-10-21 | Project docs (`AGENTS.md`, `docs/*`) are the shared memory across agents and must be updated as work progresses | Owner switches between AI agents |
| D-011 | 2026-10-21 | UI is designed in **Stitch AI** with multiple style variations; the owner picks one and shares the export zip (stored in `design/`). Style goal: catchy but simple and professional, with tiles, chips, and segmented controls preferred over dropdowns | Owner's choice. Prompts are in [UI_DESIGN.md](UI_DESIGN.md) |
| D-012 | 2026-10-21 | Add a **Vendor Admin Portal** ("SS Bills Console"), a separate hosted web app for us to track clients, issue, renew, and revoke licenses, reset device bindings, and view sales from daily summaries, with an audit log | Owner asked for a proper console. The raw Supabase dashboard is unsuitable for daily client management |
| D-013 | 2026-10-21 | **Desktop app built with Next.js + Electron.** Next.js (App Router) is built as a static export and served offline inside Electron through a private `app://` protocol. Resolves O-1 (desktop) and O-3 (Electron) | Owner chose Next.js + Electron. A static export keeps the app fully offline with no local server, and Electron allows silent thermal printing and SQLite later |
| D-014 | 2026-10-21 | Chosen UI direction: **Warm Saffron Counter** (Stitch export in `design/stitch-client-app/`). Resolves O-6 | Owner's selection after comparing Stitch variations |
| D-015 | 2026-10-21 | Features Stitch added that are outside the PRD were **left out** of the build (list in [UI_DESIGN.md](UI_DESIGN.md#deviations-from-the-stitch-export)) | AGENTS.md rule: no scope changes without owner agreement. Owner can opt any of them in later |
| D-016 | 2026-10-21 | First build step: **all screens as UI with mock data** (no database yet); billing math is real and unit-tested | Owner's choice. It validates the design and flows before wiring storage |
| D-017 | 2026-10-21 | **No left-out Stitch features are added back**, including the cash change calculator. D-015 stands | Owner's decision |
| D-018 | 2026-10-21 | **Licensing and summary sync are built after the core billing MVP.** Resolves O-2 | Owner accepted the recommendation: prove billing and printing first |
| D-019 | 2026-10-21 | **Local database uses Node's built-in `node:sqlite`** (ships inside Electron) instead of `better-sqlite3` | No native module to compile or rebuild for each Electron version. Works in Electron 45 (Node 24) and in tests |
| D-020 | 2026-10-21 | **The database, not the UI, assigns bill numbers**, inside the same transaction that marks the bill paid (`bill_counters` per financial year). Staff PINs are hashed with scrypt and checked in the main process | Gapless GST-compliant numbering must survive crashes and double clicks. PINs must not sit in the UI |
| D-021 | 2026-10-21 | ~~Demo data is seeded into an empty database on first launch~~ **Superseded by D-022** | Was a stopgap until the setup wizard existed |
| D-022 | 2026-10-21 | **A brand-new database runs a 4-step setup wizard** (restaurant, GST, Admin account and PIN, starter categories and tables). The sample restaurant is now an opt-in link on that screen. Tables and categories are soft-removed (`active = 0`) so old bills keep their labels | Real clients must enter their own details. Removing a table or category must never break past bills |
| D-023 | 2026-10-21 | **Printing goes through the Windows printer driver**, not raw ESC/POS. A receipt or kitchen ticket is HTML, loaded in a hidden window and printed silently to a named printer (or the system dialog), or saved as PDF. The same HTML drives the on-screen preview | Nearly every thermal printer sold has a Windows driver, no printer-specific code is needed, and it can be tested without hardware. Raw ESC/POS can be added later as an option if a specific printer needs it |
| D-024 | 2026-10-21 | **Vendor Console is a static Next.js web app (`portal/`) that talks straight to Supabase.** Every privileged action is a database function (`vendor_*`) that re-checks who is calling. `anon` and `authenticated` have no table access at all, and row level security is on with no policies | Hostable anywhere static, and the permission rules live in one tested place (the database), not in browser code |
| D-025 | 2026-10-21 | **Two-factor sign-in (TOTP) is required**, and enforced **in the database** (`mfa_ok()` / `require_mfa`), not only in the UI. Two vendor roles: **super admin** (everything) and **support** (view, renew, reset terminals, edit details; cannot onboard, suspend, edit plans, manage the team, or change a client's terminal limit) | A stolen password must not be enough to suspend clients or issue licenses |
| D-026 | 2026-10-21 | **One license per restaurant, allowing N terminals (PCs).** A PC binds to the license by machine ID on activation; a super admin or support can reset a binding to free a slot. Plans carry the default terminal count. This replaces the single `machine_id` in the first TRD draft | The Stitch design (and real restaurants) use more than one counter PC |
| D-027 | 2026-10-21 | **Payments are recorded by hand** (amount, method, reference) when the vendor receives money; renewing = record payment + extend. GST (18%, a setting) is added on top of plan prices. No payment gateway yet. A new period starts when the old one ends (or today if it already ended), so paying early loses no days | Keeps v1 simple and real. Razorpay links can be added later |
| D-028 | 2026-10-21 | **"Expiring soon" depends on the plan**: 30 days before a yearly license ends, 7 days before a monthly one. Grace period 7 days; "offline" = no check-in for 7 days. All are settings | A 30-day window made every new monthly license look like it needed renewing |
| D-029 | 2026-10-21 | The portal has a **browser demo mode** that runs the *same* migrations in PGlite with sample data (used whenever no Supabase project is configured) | Lets the console be explored and tested before a Supabase project exists, with no second copy of the business logic |
| D-030 | 2026-10-21 | Stitch features for the vendor console that are **not in the PRD were left out** (list in [UI_DESIGN.md](UI_DESIGN.md#vendor-console-deviations-from-the-stitch-export)). Same policy as D-015 | No scope changes without the owner. Any can be added later |
| D-031 | 2026-10-21 | **Licence answers are signed (Ed25519).** The Edge Function signs `{key, machine, state, expiry, grace_days, ...}`; the app has the public key built in and re-verifies the saved answer every time it reads it. An answer for another key or PC is rejected. The private key is the Supabase secret `LICENSE_SIGNING_KEY` (file `supabase/.secrets/`, git-ignored). **Never replace the key pair once apps are installed** | Editing the local database or faking the server must not extend a licence. Replay to another PC must fail |
| D-032 | 2026-10-21 | **The activate and sync Edge Functions run with `verify_jwt = false`** and are protected by the licence key + machine ID (checked in the database), per-IP and per-PC rate limits (`rate_limit_hit`, migration 6), request-size limits, and generic error messages | Restaurant PCs have no Supabase login. Supabase's new publishable keys are not JWTs, so the platform check would reject them anyway |
| D-033 | 2026-10-21 | **Licence lock rules on the restaurant PC:** new bills (`saveOpenBill`, `payBill`) are refused when the licence is suspended, expired past grace, not activated, or the PC has not checked in for more than `grace_days` (7). History, reports, backup and settings stay open. A PC that sets its clock back gains nothing (latest time seen is remembered). Activation comes before the setup wizard | TRD §7.4, PRD L-1/L-2. Owner asked for the critical gaps to be closed |
| D-034 | 2026-10-21 | **Wrong-PIN lockout:** 5 wrong PINs in a row lock that user for 1, 2, 4, 8, then 15 minutes; a correct PIN resets it; the count survives restarts | A 4-digit PIN can be guessed at the keyboard otherwise |
| D-035 | 2026-10-21 | **Backups are `VACUUM INTO` snapshots** in a folder the user picks (default `Documents\SS Bills Backups`; USB works). Automatic once a day while the app runs, newest 30 kept; manual and "saved before a restore" copies are never deleted. Restore validates the file (integrity check, SS Bills tables, not newer than the app), saves current data first, swaps the file, restarts. O-4 (off-site copy) is still open | A backup on the same disk does not protect against a lost PC; the screen says so |
| D-036 | 2026-10-21 | **`SSBILLS_LICENSE=off` and `SSBILLS_API_URL` only work in an unpackaged (development) run**; an installed app ignores them. The "last check-in" time is taken from SS Bills' own clock (`server_time` in the signed answer), not the PC's. The app window can only show its own pages (navigation blocked) and refuses every permission request | An environment variable must never be able to switch licensing off. A PC with a wrong clock must not be able to fake a recent check-in |
| D-037 | 2026-10-21 | **Licence keys can be replaced** from the client page (super admin, reason required, migration 7 `vendor_regenerate_key`). The old key stops working at once; PCs already linked stay linked and re-activate with the new key without using a terminal slot; they show "Activate again" and cannot create new bills until then. The activity log keeps only the last 4 characters of each key | A leaked key must be revocable without suspending the client or losing their data |
| D-038 | 2026-10-21 | **Installer: electron-builder, NSIS, Windows 64-bit, per user**, with `asar` off (the static pages are served from plain files). Only `electron-updater` is a runtime dependency (Next, React and fonts are build-time only, which keeps the installer at ~117 MB). Uninstalling never deletes `%APPDATA%\ss-bills`. Icon is generated into `app/assets/` by `app/scripts/make-icon.cjs` (the `.ico` is written without an image tool because the converter runs out of memory on small PCs). Unsigned until the owner gets a certificate (docs/RELEASING.md) | Smallest working installer; a customer's data must survive uninstall and reinstall |
| D-039 | 2026-10-21 | **Updates:** the app reads `updateUrl` (in `license-config.json`) every 6 hours, downloads quietly, and installs **only when the app is next closed**, never mid-service; failures are silent and retried. Switched off in development and until `updateUrl` is set. **Database safety:** before an update changes an existing database the app keeps `ssbills.db.before-vN.bak`; an older app refuses data from a newer schema and says so; the database is closed if opening fails | Updates must never interrupt billing or silently damage data |
| D-040 | 2026-10-25 | **Central database backups are logical dumps made by `supabase/scripts/backup.ps1`** (`pg_dump` of schema `public` through the session pooler, read-only), with a manifest of checksums, row counts and the console team list. **Auth (logins, password hashes, 2FA secrets) is deliberately not backed up**: a stolen backup must not unlock the console; logins are re-created from the manifest. Restores are proven by `restore-test.ps1` in a throw-away local Postgres using the same recipe a real recovery needs (skip `CREATE SCHEMA public` and the `vendor_admins` rows, no superuser tricks, re-create team rows). A real restore goes into a NEW project, never over a live one. Procedure: [BACKUP.md](BACKUP.md) | Free Supabase has no backups; the direct database host is IPv6-only and unreachable on most home networks; Supabase's `postgres` role is not a superuser |
| D-041 | 2026-10-25 | **When the restaurant app checks in with SS Bills:** (1) in the background ~10 seconds after start, (2) in the background at every successful login (`license("touch")`), (3) routinely every hour while open (checked every 15 minutes), 15 minutes after a failed attempt. Any request is ignored if the last attempt was under 5 minutes ago or one is running. A check-in never blocks login or billing; a failure is silent. **The offline allowance stays 7 days** (owner's decision): a suspended PC that is kept offline locks 7 days after its last good check-in; an online PC learns of a suspension within the hour or at the next login. **The "last check-in" time is now the `server_time` inside the signed answer**, so editing the local database cannot extend the allowance, and the PC clock can never run before the last signed answer | Owner asked how a non-syncing PC could dodge a suspension. Offline-first means a suspension can only reach a PC when it connects, so the controls are frequent check-ins plus a hard offline limit that cannot be edited away |

| D-042 | 2026-10-25 | **One PC per licence.** Every plan defaults to 1 terminal (migration 8). A super admin can still raise one client's limit, and the console then warns that **each PC keeps its own separate data: the menu is not shared and bill numbers repeat across PCs** (a GST problem). A real multi-PC mode (shared data, per-terminal bill series) is not built | The owner chose to sell one PC per licence for now; the data model has no sharing between PCs |
| D-043 | 2026-10-25 | **A cloud copy of the restaurant's menu and settings** (resolves O-10). Contents: profile and receipt text, GST settings, categories, menu items, tables. **Never**: bills, held bills, staff, PINs, staff phones, printer names, licence data (staff left out; the owner's "approve all" was read as the safer default; the Admin is recreated with a new PIN). Stored in `menu_snapshots` (newest 10 copies per restaurant, 1 MB cap, identical menus not stored twice), reachable only through the `menu` Edge Function by an **activated, bound PC on a licence that is not suspended or expired**; the console never shows menus. Saved after each good check-in and a minute after the menu changes; restored only into an **empty** PC from the setup wizard, with a new Admin name and PIN. A restore answer is **signed** and every field is strictly checked before use. The database also refuses any field outside the agreed list, so a PIN cannot be stored even by a modified app. **The privacy notice must say the menu and settings are stored** | A lost PC must not mean retyping the menu; the exclusions keep a stolen copy harmless |
| D-044 | 2026-10-25 | **Menu import and export as CSV** (Excel and Google Sheets). Import is **all or nothing** (any bad row refuses the file, with line numbers), **never deletes**, matches existing items by category + name (ignoring case), previews what will change and applies it by a one-time token (the screen never supplies rows or paths), reads Excel's UTF-8, plain-CSV (Windows-1252) and UTF-16 files, accepts comma, semicolon or tab, and the export protects cells beginning `= + - @` from being run as formulas | Typing a first menu is the biggest day-one chore; a half-imported or silently overwritten menu would be worse |
